# PRD-458 — Streamed open worlds hold 60 fps with no per-game tuning

**Status:** IN PROGRESS — filed 2026-09-27; Phase 1 part A (clustered shared batches, AC-1) landed 2026-09-27; AC-2's engine and three layers landed and unit-green, its browser proof open; AC-3 mapped but not started.
**Priority:** P1 — Open: one virtual shadow level per frame, zero streamed shadow builds, 60 fps by default.
**Complexity:** 7 (HIGH): 11+ implementation files, a new clustered-batch system, streaming state across frames. Risk override: none.
**Owner:** engine
**Depends on:** [PRD-459 smooth streaming](PRD-459-smooth-streaming-one-admission-budget-per-frame.md) (per-frame admission budget, prefetch, pipeline prewarm), [PRD-453 per-instance LOD](PRD-453-worldcells-use-existing-lods.md), [PRD-456 distant cell proxies](PRD-456-distant-world-cell-proxies.md), [PRD-457 shadow pages](../Unreal/rendering/PRD-457-virtual-shadows-scale-by-measurement.md), and [PRD-377 AutoLOD on by default](../assets/PRD-377-auto-lod-is-on-by-default.md). This PRD owns only what those leave out (below). It does not repeat their work.

## Context

Unreal 5 keeps a dense streamed world at 60 fps without the game tuning anything. GPU Scene uploads only dirty instances. Virtual Shadow Maps re-render only the pages that changed, with instances culled per cluster per page. Nanite and automatic LOD cover foliage, and HLOD merges distant cells and their materials. World Partition streams under a per-frame time budget. ThreeNative is building the same pieces (PRDs 453–457 and 459–461). This PRD closes the gaps the machinefall 2 km map exposed and turns "60 fps by default" into a gated promise.

**Evidence** (machinefall `?scene=map-walk`, RTX 2080 WebGPU, 1600×900, Xvfb + `TN_FRAME_BUDGET`, 2026-09-27). The fixes already landed in #358 took a walk from ~160 ms CPU / 103–130 ms GPU per frame (11.5 s freezes) to ~30 ms CPU / 20–27 ms GPU. What remains is structural:

## Solution

1. **Clustered shared batches.** Each `asset:level:part` shared batch splits its records into spatial clusters (default: world-grid squares of about one cell) with their own bounds. Each cluster is its own InstancedMesh, pooled with a stable uuid so three's node cache holds. Main and shadow level cameras cull clusters through three's normal frustum path, so a 48 m level submits only the clusters it covers. This replaces the `shadows.castDistance` companion stopgap: casting is now bounded by what each level can see, not by a hand-tuned radius. Cluster size is measured, not guessed: pick the smallest size that keeps main-pass draws within 1.3× today's.
2. **Shadow passes schedule safely.** Re-render at most one due level per frame, finest first. Fix the depth-texture lifetime so a deferred level render never destroys a texture the current frame binds: recreate before the bind group is built, or retire it at frame end.
3. **Shadow-context prewarm.** Every streamed key's clusters get their shadow-context node built during admission (behind PRD-459's budget), not on first shadow draw.
4. **Foliage gets automatic LOD.** The cook converts qualifying `BLEND` foliage (alpha from a texture, no true translucency) to alpha-tested with alpha-to-coverage (`renderer.alphaAntialiasing` already exists). AutoLOD accepts `MASK` primitives with a card-preserving reducer: it keeps every primitive and material, reduces cards, and clamps UV and alpha coverage. It does not collapse primitives, which is what lost needle materials in machinefall's earlier LOD1. A level must still save ≥ 20% (`minSaving`); PRD-456 proxies take over beyond the last level.
5. **Materials merge in the cook by default.** `dedupeMaterials` runs by default, and scatter textures that share a shader signature pack into atlas pages, so batches that differed only by texture share one material. `pnpm census:content` reports the before and after.

Consumer flow: a game calls `WorldCells.load({ … })` with no performance options → the cook (`threenative build`) bakes cutout foliage, LOD chains and deduped materials → WorldCells streams clustered batches → the renderer culls clusters per camera and schedules shadow levels → `TN_FRAME_BUDGET` reports the frame.

Risks:
- Clustering multiplies meshes (node builds, draws). Mitigated by pooling, prewarm and the 1.3× main-draw cap.
- Cutout conversion changes the look of soft-edged translucency. Mitigated by eligibility only for texture-alpha materials, plus a per-asset override.
- Atlasing breaks tiling UVs. Mitigated by atlasing only textures whose UVs stay within [0, 1].

## Decisions
- 2026-09-27 (owner): 60 fps is required. Do it automatically in the engine, Unreal-5-style, in as few PRDs as possible. Build on PRDs 453–457 / 459–461 instead of duplicating them.
- 2026-09-27 (agent, measured): BatchedMesh is rejected for draw merging (three r185 WebGPU draws per instance). Merge draw count through clusters plus material dedupe instead.
- 2026-09-27 (agent, measured): `clusterSize` defaults to the package `cellSize` — a cluster is a whole number of cells, so a record is clustered only when its own cell is admitted or evicted and nothing is ever re-clustered. `2 x cellSize` halves the meshes and misses the shadow bound by the same amount (34 vs 32 worst draws per level render), so it buys nothing on the fixture and stays the game's override. The 1.3x main-draw cap is not met at either size; see the AC-1 line.
- 2026-09-27 (owner, decision): **clusters are for shadow casting only.** The main view keeps ONE mesh per `asset:level:part` — the pre-3aa368f64 behaviour, so main-pass draws are unchanged — and the same records are written again into one caster-only mesh per `(key, cluster)`, alone on `VIRTUAL_SHADOW_CASTER_LAYER`: the level cameras draw that layer and the main camera never does. The main mesh sets `castShadow = false`; the caster clusters carry the shadow. Caster clusters are culled per level camera, pooled with stable uuids, and minted and prewarmed with their key. No `castDistance` radius — the option stays accepted, validated and a documented no-op. Reason: cluster per cell is what makes the shadow cull work, and the main camera sees the whole ring, so it paid for every cluster in it (10 -> 70 draws) at ~75 us a draw — a net loss at machinefall scale.
- 2026-09-28 (agent, measured): a level render is a `renderer.render` call, so three's per-render `updateBefore` keying re-enters `VirtualShadowNode.updateBefore` from inside the node's own grant. A per-`updateBefore` budget therefore admits one level per *render call*, not per presented frame. The fix is a re-entrancy guard, not a frame id: `frame.frameId` is incremented by `_renderScene` too, so it cannot name a presented frame, and the nested call carries no work the outer one has not already done.
- 2026-09-28 (agent, measured): the per-level shadow draw count at 2 km is set by the level camera's *depth*, not its width. With `cellSize` 128 m and `far = lightDistance + depthRange = 600`, a 48 m fine window crosses ~9 clusters per key and submits 493 of 2203 live caster meshes; a 640 m coarse window submits 2674. `clusterSize` does not help — a smaller cluster raises the count (`footprint/c^2 + perimeter/c` is 13.7 at 128 m, 79 at 32 m) — so the only levers are `depthRange`/`clipExtents` (a look change, the game's) or culling clusters in light space per level.
- 2026-09-27 (agent, measured): the depth-texture validation error was never the schedule's fault. three's `Textures.updateRenderTarget` re-versions a render target's depth texture the first time that target is registered, which is after the main pass has already bound it; and `Textures.updateTexture`'s re-version branch calls `backend.destroyTexture` without dropping `textureData.bindGroups` the way `_destroyTexture` does, so a bind group keeps naming a destroyed GPUTexture. Both layers are now fixed — the node renders one level per frame and gates every level's sample behind its own `mapped` uniform so a level is never read before it has drawn, and the patch drops the stale bind groups. One level per frame is a win in its own right: a level render is a whole scene draw.
- 2026-09-27 (agent, measured): the split's cost and win on the flythrough fixture: 28 caster clusters and 28 extra segment writes per admitted cell against 0 extra main-pass draws; a 48 m level window went from 614 draws (one mesh per key, ring bounds) to **15 median / 17 worst**, and the main pass is back to 10 draws for 10 keys. `shadows.cast` off means no caster half at all, so a world that never asks to cast pays nothing.
- 2026-09-27 (owner, decision): `display.maxFps` **follows the display** — the panel's own refresh rate capped at 120 on desktop and web, 60 on mobile (power and thermal), an explicit number still winning and `0` still uncapping. Every template shipped `maxFps: 60`, so a 120 Hz desktop played at half its panel and the author had no signal that the config had already answered the question. There is no browser refresh-rate API, so on the web the rate is *measured*: the median presented interval over a frame-budget window is the vblank period (one rAF callback is one present), snapped to 60/75/90/120/144/165 and capped at 120; a native host says its own rate through the present counter. Until a window has measured one the answer is 60 and reports `targetSource: "fallback"` rather than claiming the display's. One resolver, `resolveTargetFps(config, platform, measuredRefreshHz)`, is the only reader of `display.maxFps`, and `TN_FRAME_BUDGET` reports its result and source on every window so a harness can assert the rule. `maxFps: 0` means uncapped, which is a game with no frame budget and therefore no adaptive resolution scaler.
