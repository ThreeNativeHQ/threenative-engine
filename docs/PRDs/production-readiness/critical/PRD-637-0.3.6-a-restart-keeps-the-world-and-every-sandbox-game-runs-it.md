# PRD-637 — 0.3.6: a restart keeps the world, a fresh install passes its own clean room, and every sandbox game runs it

**Status:** NOT STARTED
**Priority:** P0 — 0.3.5 is `latest` on npm, and its CI clean room is red: `npm install` crashes (AC-4b), the native starter cannot execute (AC-4c), Android builds fail (AC-3), and a restart can drop the world (AC-1, AC-2).
**Complexity:** 6 (MEDIUM); risk override: none. Touches 3-6 engine files (+1), crosses the npm and GitHub release boundary (+2), works with complex scene-transition state (+2), and talks to the registry (+1).
**Owner:** engine runtime
**Depends on:** PRD-624 (0.3.5 release, done apart from close-out). PRD-629 (release in one command) shortens Phase 3 but is not required.

In the same clean room, two failures come from this desktop and not from the product. `doctor`
correctly reports a Wayland session with no X display and JDK 27. `native` hit an Xvfb display-number
collision. The CI clean room separates the two kinds: a red there is a product bug.

Files to inspect first: `packages/core/src/renderer.ts` (`createRenderChain`, which disposes the
previous chain on a scene change), `packages/core/src/render/chain.ts`, the scene-transition path in
`packages/core/src/game.ts` (`goto`, the loader-frame hold), the native web engine's chain and pass
disposal in `packages/runtime-native/src/engine/`, and the Android bundle step in
`packages/runtime-native/scripts/bundle.mjs`.

## Solution

1. **Make the restart failure deterministic first.** A restart-loop scenario restarts the starter N
   times on a cold, freshly cooked project and asserts the world after each one. Run it on the
   native web engine with `--browser-recipe webgpu` and a named adapter. Find out whether the world
   is absent for a bounded number of frames (a held draw while the new chain compiles) or for
   good (a disposed chain, pass or target still bound). Fix the engine layer that owns the cause.
   The fix is never a longer wait in the scenario (playtest AGENTS: "Never fix a boot race by
   lengthening a wait").
2. **Fix the Android bundle** so that a module with a top-level await is never inlined into a
   non-async initializer, or so that the native bundle target keeps such modules at the top level.
   Then fix the iOS consumer fixture: write the two files it imports, or remove the imports.
3. **Ship 0.3.6 through the normal chain,** and run the CI clean room (`npm-release.yml`,
   `clean_room_only`) against the published cohort. Then move every sandbox game that depends on
   core onto 0.3.6 **from the registry** (the user-like install). Lane tarballs move only after
   their lane change is confirmed in 0.3.6. A lane change that is not in 0.3.6 keeps its tarball,
   with the reason recorded in that game's `FRICTION.md`.
