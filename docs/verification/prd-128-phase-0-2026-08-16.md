# PRD-128 Phase 0 — where the physical Android qualification actually exits

2026-08-16. [PRD-128](../PRDs/native/PRD-128-android-qualification-split.md) Phase 0 says to
run `native:qualify:physical --platform android` against the Pixel 8 **before moving any file**, and
pre-commits two outcomes: it exits on the signing check, and the split proceeds; or it exits earlier,
and that earlier thing is a fifth blocker nobody recorded and gets written down first.

**It exited earlier. The command does not exist on `main`.** The split's premise is still correct —
it was confirmed separately, see §2 — but the cost is not the one PRD-128 priced.

PRD-056 is filed `PLANNING COMPLETE; EXECUTION BLOCKED`, and on `main` that description is exact:

**But it was written.** `linchpin/prd-056-physical-mobile-qualification` carries two commits —
`8bcf0553 feat(native): add physical mobile qualification contract` and
`8bba6603 fix(native): repair physical mobile qualification evidence` — totalling roughly 3,200

**That branch is 2 commits ahead of `main` and 219 behind it.** It has never been merged, and the
drift was measured rather than guessed at: cherry-picking the first commit onto `main` conflicts in

Six of the seven are mechanical. The seventh is not, and it is the reason this branch cannot simply
be landed.

### The C++ conflict is `main` refusing a fix it has already tried on this phone

At the Android resize path, the branch adds:

```cpp
if (webgpu_ && !platform::isBackgrounded() && e.width > 0 && e.height > 0) {
    webgpu_->resizeSurface(static_cast<uint32_t>(e.width), static_cast<uint32_t>(e.height));
}
```

`main` has, at that exact site, a comment left by someone who did that and watched it happen:

> The swapchain is deliberately NOT reconfigured here, and `Runtime::resize()` — which would — is
> still unreachable. Calling it from this path was tried and aborts the process: a launch rotates the
> display twice before the first frame, and reconfiguring the surface from inside the resize callback
> tears it down under the frame in flight. **A Pixel 8 died with signal 6 immediately after
> `TN_NATIVE_SMOKE_FIRST_FRAME`.** … Doing this correctly means deferring the reconfigure to a frame
> boundary, where no surface texture is acquired. That is real work and is not attempted here.

The branch's guards (`!isBackgrounded()`, positive dimensions) do not address the described cause,
which is reconfiguring under a frame in flight rather than reconfiguring while backgrounded.

**So the branch is not merely stale: part of it is an approach `main` has since rejected with device
evidence, on this same Pixel 8.** Landing it wholesale would reintroduce a crash whose autopsy is
already written in the file it conflicts with. The C++ half has to be redone against what `main`
learned; the orchestrator and its tests are the part worth recovering.

### This is the fifth blocker, and it is a different kind from the other four

PRD-128's table lists four external dependencies — Android hardware (have it), an Android signature
(owner decision), Apple hardware (nobody has it), Apple signing (nobody has it). The fifth is not
external at all:

> **The qualification orchestrator PRD-056 planned was built, works, and was never landed.**

Nothing outside this repository has to change to clear it. It is the cheapest of the five and the
only one that was invisible, because a `BLOCKED` folder makes an unlanded branch look like an
unwritten one.

## 2. On the branch: it exits exactly where PRD-128 predicted

Run from the `prd-056` worktree against the attached Pixel 8, the orchestrator reaches the device
gates and refuses before any of them:

| # | Invocation | Exit | Code |
| --- | --- | --- | --- |
| 1 | `--platform android --device 37251FDJH0037Z` | **2** | `TN_QUALIFY_SIGNING_REQUIRED` — *"Android artifact is missing at null."* |
| 2 | …`--android-app tn-android-v8.apk` | blocked | `TN_QUALIFY_SIGNING_TOOL_REQUIRED` — *"apksigner is unavailable; production signature cannot be verified before adb install."* |
| 3 | …same, with `apksigner` on `PATH` | blocked | `TN_QUALIFY_ARTIFACT_PROVENANCE_REQUIRED` |

**PRD-128 §2 is confirmed on evidence: signature verification is a precondition of everything on the
Android path, and it blocks before the device is touched.** The phone was attached, awake, at 72%
and `Thermal Status: 0` for all three runs, and not one of them read a property from it. The split
this PRD proposes is the right shape.

### And a sixth thing, which is a defect rather than a blocker

Run 2's `TN_QUALIFY_SIGNING_TOOL_REQUIRED` is wrong about its own machine. `apksigner` is present —
`/home/joao/Android/Sdk/build-tools/{34,35,36}.0.0/apksigner` — it is simply not on `PATH`. The
engine load test solved this exact problem for `adb` in `scripts/engine-load-test/run-android.ts:39`
by falling back to the SDK's copy, with the comment *"`adb` is not on PATH on this machine; the SDK's
copy is."* The qualification script has no equivalent, so it reports a missing capability where the
truth is a missing lookup.

That matters more than a one-line fix, because it is the shape of blocker this whole exercise is
about: **a lane that reports "blocked, tool unavailable" reads identically whether the tool is absent
or merely unfound, and only one of those is a blocker.**

## 3. What this changes about PRD-128

Nothing about the split's direction; a good deal about its cost and its order.

- **Phase 1 (move the folders) is unchanged and still correct.** The three claims genuinely have
  three different blockers.
- **Phase 2 is not "separate the existing Android path from the signing path".** There is no existing
  path on `main` to separate. Phase 2 first has to recover ~3,000 lines from a branch 219 commits
  behind, and the recovery is not a cherry-pick: the orchestrator, the evidence module, the fixtures
  and the tests come across as mechanical conflicts, while the C++ resize change must be dropped
  rather than merged, because `main` rejected it with a signal-6 crash on this phone.
- **PRD-128's cost line — "a split, three folder moves, and then the runs" — is wrong**, and its
  complexity rating of 6 is low. The runs are still the cost, but recovering the orchestrator is now
  ahead of them, and it carries a C++ decision the split PRD does not mention.
- **The recovery is worth doing and should be its own PRD.** It is one branch, a known conflict set,
  and a named thing to drop. Folding it into PRD-128 would hide a C++ crash decision inside a document
  whose subject is folder names.
- **Its §1 present-tense claim about `qualify-physical-mobile.mjs:253`-style specifics should be
  restated** as describing the branch, not the tree.

**No folder was moved.** PRD-128 §9: *a PRD split that leaves the work still blocked is worse than the
union it replaced, because it spends the honesty of three folder names and buys nothing.* Moving A
into an active folder today would put a runnable label on work whose runner is on an unmerged branch.

## 4. What this file does not claim

- **Nothing was qualified.** No device gate ran. The phone was attached and never read.
- **Not mobile-ready, and not Android-qualified.** One phone is not mobile, and zero executed gates
  are not a qualification.
- **The two branch commits were not reviewed for correctness**, only executed far enough to observe
  where they stop. That they run is not that they are right.
- **PRD-128's signing claim was checked and holds**: `packages/runtime-native/android/app/build.gradle.kts:253`
  declares `release` with `isMinifyEnabled = false`, proguard files and **no `signingConfig`**, and
  `grep -rn signingConfig packages/runtime-native/android/` returns nothing. There is no keystore
  tracked in the tree.
