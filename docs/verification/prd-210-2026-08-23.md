Rung 2 was run three times. The first two are void and no part of them is used: `am start` was

### Rung 3 — screen-off stops presenting. PASS, with a caveat on the marker.

Screen on, presenting at 60 Hz; `KEYCODE_SLEEP`; 15 s. One further 60-frame tick was emitted and
then presenting stopped — against bug 9's recorded baseline of a full 60 s of continued presenting.
Tick granularity is 60 frames, so this bounds the pause at about a second but does not measure it;
"within ~1 s" is consistent with the data and is not independently established by it.

The caveat is real and worth carrying: **no `TN_LIFECYCLE` marker is observable while the app is
paused.** All of them — including `{"event":"paused","applied":true}` — arrive in one burst at the
instant of resume. The reason is structural and is the same fact that made a watch necessary: the
watch sets the flag synchronously, but the thread that writes markers is then parked inside SDL's
`Android_WaitLifecycleEvent`, so it cannot write anything until SDL lets it go. The pause is
applied correctly; only its reporting is deferred. A gate that watches for a live "paused" marker
on Android will wait forever.

### Rung 4 — resume. FAIL, and it is this change's own defect.

Waking resumed the loop, and the loop presents nothing:

```
# before backgrounding
TN_PRESENTS_TICK:{"frames":720,"presents":720,...}
# 12 s off, 12 s back
TN_PRESENTS_TICK:{"frames":10080,"presents":781,...}
TN_PRESENTS_TICK:{"frames":10740,"presents":781,...}
```

`frames` runs away at roughly 600/s while `presents` stays frozen. A `screencap` after resume is
uniformly black; one taken before it shows the scene. Android destroyed the `ANativeWindow` on
background and the `WGPUSurface` still points at it.

PRD-210 asked for exactly this and the implementation did not carry it: *"Surface revalidated like
startup does."* Filed as
[`../bugs/resume-presents-nothing-2026-08-23.md`](../bugs/resume-presents-nothing-2026-08-23.md).
**The pause half of this PRD is not shippable until that lands**, and it is already on `main` as
`5989e4a2`, so it needs either the surface fix or a default of `"continue"` in the meantime.

**Both happened, in that order.** `c3ae3b26` took the interim default, and the surface fix landed on
2026-08-23 with its own red/green on this phone
([`resume-presents-2026-08-23.md`](resume-presents-2026-08-23.md)), which returned the default to
`"pause"`. This section is left as it was measured.

Battery 35 %, 32.1 °C, Thermal Status 0 at the end. Both debug properties were reset to `0` and the
app force-stopped; the screen-off timeout was read (1 800 000 ms), briefly changed, and restored to

**Finding: on Android, SDL parks the loop thread itself.** No frame runs while the app is in the
background in any of the three builds. SDL 3 blocks the event pump inside
`Android_WaitLifecycleEvent` (`SDL_HINT_ANDROID_BLOCK_ON_PAUSE` defaults to on, and the runtime
never sets it). So on Android:

- the host's pause flag is not what stops presents, and removing it does not re-redden the rung;
- the flag still suspends audio, counts dropped timers and writes the markers;
- `backgroundMode:"continue"` cannot keep frames running, and its markers say so (`applied:false`).

`continue` overrides pausing on desktop (above). Letting it run frames on Android would mean
clearing the hint and running JavaScript against a destroyed surface. That is a product decision,
recorded in the PRD.
